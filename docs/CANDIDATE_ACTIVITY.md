# Candidate activity

The Applications tab shows seven recent recorded milestones above the application filters, with an upcoming panel and current status beside it. **Show 7 more** appends older entries. **Show All Activity** sits beside it in the centred footer and opens `/candidates/[id]/activity` in a new tab. The full-width page shows 20 entries per page, with Jobs-style numbered pagination, Prev/Next, and Page/Go. Both views keep details collapsed under Show more, use coloured status badges, and show important details in two or three columns on wide screens and one on narrow phones. Source and meeting links open in new tabs. Mock feedback links target that session in Training Audit.

Candidate cards request one upcoming item together with the candidate list. A single batch query covers the visible candidates. Activity and candidate cards refresh every 15 seconds while visible and on focus. Custom saves refresh the current view immediately and broadcast to other local tabs. Expanded compact history stays stable until Refresh is chosen. Training Audit keeps the rating, course percentage, progress bar, and mock count in two compact rows.

Activity comes from interview audit records and schedules, preparation-document and recording changes, training notes, mock reports, OPT changes, and candidate status changes. Generic application status transitions (such as "Application interview"), bulk application logging, pipeline retries, automatic status-rule follow-ups, sync/import timestamps, and auto-generated copies of mock feedback notes are excluded. Current training progress is a snapshot, not a fabricated historical change. Going forward, training record changes and their before/after activity entries are saved in one SQL statement.

The full history page uses the available desktop and mobile width. Recorded interview changes and current interview details are separate, so an earlier reschedule retains its original old/new times. Current stage details can include appointment, format, duration, location, preparation/staff notes, and mock-answer state, with links to the application and available meeting/job posting. Mock reports show stored feedback, strengths, improvements, and transcript/document availability; raw transcripts are read in their source report.

Upcoming items are active future interviews, explicitly sourced pending follow-ups, and the existing OPT approval-date-plus-90-days window. Cancelled/completed interviews, closed or rejected applications, completed follow-ups, and incomplete OPT approval dates do not generate upcoming items. A mock feedback report is never treated as a scheduled mock appointment. The inspected local database contains no mock scheduling table, and its separate audit-calendar bridge is not configured; no upcoming mock time is inferred from feedback or notes.

The feed only reconstructs stored evidence. Previous training status changes that were never logged cannot be recovered. A missing timestamp does not become an event at the current time. Unavailable sources are reported in the view, and failed candidate-card enrichment shows unavailable rather than claiming no upcoming activity. No AI calls are used.

## Custom activities

Migration `147_candidate_custom_activities.sql` adds custom records. Title and reason are mandatory; a web link and dates are optional. Activity dates offers No date needed, Single day, Multiple days, or Multiple days with start and finish time. Dates and time conversion use the candidate's saved timezone, enforced again by the API. A candidate without a saved timezone can receive an undated activity. Date-only ranges retain their calendar days; invalid or ambiguous local times are rejected.

All staff roles may create, edit, or delete except `application_engineer_grunter`. Controls are hidden for that role and every mutation is independently blocked in the API. Saves use record versions to prevent lost edits; changes and before/after audit snapshots commit together. Deleting hides the activity from history and Next up while retaining a recoverable row and audit trail. Upcoming and ongoing custom records participate in the same one-item candidate-card query as other upcoming items.
